# После обновления Antigravity

Desktop, IDE и CLI обновляются независимо. При включённом автопатче работающая фоновая служба ждёт, пока файлы обновления перестанут меняться, и проверяет знакомые сборки. Если вы вручную отключили патч, служба сохраняет этот выбор.

## Как проверить обновление

1. Дождитесь завершения обновления Antigravity. На вкладке **«Обзор»** нажмите **«Проверить»**.
2. Найдите отдельную строку для каждого клиента, которым пользуетесь. Если нужной установки нет, откройте **«Установки»**, нажмите значок папки **«Указать путь вручную»**, введите путь к каталогу и повторите проверку в «Обзоре».
3. Запустите именно обновлённую копию клиента и выполните привычное действие. Например, в Desktop или IDE отправьте обычный запрос и дождитесь ответа. Результат для CLI проверьте отдельно.

| Результат проверки | Как его читать |
|---|---|
| «Ещё не проверено» | Результата для этой установки пока нет. Дождитесь окончания проверки и сверьте путь. |
| «Патч применён» | Проверку прошли все обнаруженные нативные файлы этой установки. Запуск, вход в аккаунт и ответ сервиса проверяются в клиенте. |
| «Патч не подтверждён» | Проверка не подтвердила состояние всей установки. Разобраться, какой файл затронут, поможет отчёт `--status`. |
| «Сигнатура не найдена» или сообщение о незнакомой сборке | Анлокер не распознал этот файл. Сохраните версию клиента и точное сообщение, чтобы можно было проверить совместимость со следующим выпуском. |
| «Не читается» или ошибка записи | Сохраните путь и текст системной ошибки. На Mac при отказе в записи проверьте разрешение «Управление приложениями». |

На Mac отчёт можно получить в Терминале

```sh
"/Applications/Antigravity Unlocker.app/Contents/MacOS/ag_unlocker" --status
```

В отчёте видны результаты по отдельным файлам. В Desktop и IDE это может быть `language_server` — фоновый компонент клиента. Для CLI проверяется его исполняемый файл. Настройка автопатча и состояние службы выводятся отдельно. Если результат расходится с поведением клиента, сверьте путь установки из отчёта и версию в запущенном приложении. [Коды выхода и разрешения macOS](../macos/README.md)

## Где найти журнал

**«Журнал» → «Скопировать журнал»** копирует в буфер до 400 последних записей текущего сеанса. Вставьте их в файл до закрытия окна или деактивации. Если обновление произошло при закрытом окне, возьмите записи фоновой службы за время сбоя.

| ОС | Файл журнала службы |
|---|---|
| macOS и Linux | `~/.local/share/agunlocker/watchdog.log`. При заданной непустой `XDG_DATA_HOME` — `$XDG_DATA_HOME/agunlocker/watchdog.log`. |
| Windows | `%LOCALAPPDATA%\AGUnlocker\watchdog.log` |

Команды PowerShell для чтения журнала и сохранения отчёта приведены в [руководстве для Windows](windows.md).

Служба создаёт журнал при первой записи и ограничивает его размер. Для разбора сбоя сохраните название клиента, версии клиента и анлокера, ОС, время, точный текст ошибки и строки за этот период.

## Как вернуться к штатной установке

1. Сохраните работу в Antigravity и скопируйте нужные журналы. Полная деактивация закрывает клиенты и при успешном завершении удаляет службу и её данные.
2. Выберите **«Установки» → «Полная деактивация»**, затем **«Деактивировать»**. В Windows для этой операции нужны права администратора.
3. После сообщения **«Анлокер полностью деактивирован»** откройте клиент и проверьте его запуск. Если появилось **«Деактивация не завершена»**, сохраните новые строки журнала, устраните указанную причину и повторите операцию.

Деактивация снимает изменения с найденных и вручную добавленных установок. Версия самого Antigravity остаётся установленной. На Linux копия анлокера и ярлык, созданные для меню приложений, удаляются отдельно. [Руководство для Linux](../linux/README.md)

## Сборка и выпуск для Mac

Версия приложения берётся из `Cargo.toml` и совпадает с версией Antigravity, для которой выпущен анлокер: `2.35.2` — для Antigravity 2.35.2. Исправления анлокера между выпусками Antigravity нумеруются через подчёркивание: `2.35.2_1`, `2.35.2_2` и так далее. `Cargo.toml` при этом не меняется, а полную версию передаёт переменная `AG_FULL_VERSION`. Окно показывает полную версию и считает `2.35.2_1` новее `2.35.2`, поэтому пользователи получают уведомление об исправлении.

| Что выходит | `version` в `Cargo.toml` | Тег |
|---|---|---|
| Выпуск под новую версию Antigravity | `2.35.3` (поднять, затем `cargo update -p ag_unlocker`) | `v2.35.3` |
| Исправление анлокера | не меняется | `v2.35.2_1`, `v2.35.2_2`… |

На Mac с инструментами командной строки Xcode и установленным через rustup Rust выполните из корня репозитория

```sh
rustup target add aarch64-apple-darwin x86_64-apple-darwin
macos/build.sh
```

Скрипт собирает обе архитектуры, проверяет их наличие в универсальном бинарнике, подписывает бинарник и приложение локальной подписью ad hoc с hardened runtime. Затем он проверяет подпись приложения, запускает его с `--version`, упаковывает файлы и проверяет целостность DMG. Готовые файлы появляются в локальном каталоге `release/`. [Скрипт сборки](../macos/build.sh)

| Файл универсальной сборки | Содержимое |
|---|---|
| `Psychotic_AG_Fork.dmg` | Приложение, ярлык Applications и руководство для Mac |
| `AG_<версия>_macOS_universal_app-local.zip` | Приложение для распаковки в Finder |
| `AG_<версия>_macos.tar.gz` | Папка с бинарником, скриптом `Запустить.command` и руководством |

Локальная сборка исправления: `AG_FULL_VERSION=2.35.2_1 macos/build.sh`. Для быстрой локальной сборки на Apple Silicon есть `macos/build.sh --arm64-only`. В этом режиме ZIP получает суффикс `arm64_app-local.zip`, а имена DMG и TAR.GZ совпадают с именами универсальных пакетов. Чтобы сохранить оба комплекта, создайте второй выходной каталог и передайте его через `--out`.

### GitHub Actions

- При пуше в `main`, в pull request, при пуше тега `v*` и при ручном запуске workflow выполняет тесты для Apple Silicon.
- При пуше тега `v<версия из Cargo.toml>` или `v<версия>_<номер>` после успешных тестов CI запускает тот же скрипт сборки с полной версией из тега и прикладывает три файла к релизу. Тег другого вида останавливает сборку до компиляции.
- При ручном запуске пустое поле `release` сохраняет файлы как артефакт запуска. Для выпуска из существующего тега выберите сам тег как исходную версию workflow и укажите этот же тег в поле `release`. При повторной публикации CI заменяет одноимённые файлы релиза.

[Конфигурация workflow](../.github/workflows/macos.yml) · [Релизы форка](https://github.com/Breakdownx/psychotic-fork/releases)

### Подпись и проверка готового пакета

Универсальная сборка в этом workflow получает подпись ad hoc. Проверить целостность локального образа и подпись приложения, извлечённого из опубликованного ZIP, можно на Mac. Откройте Терминал в каталоге с обоими файлами. Пример для версии 2.35.2

```sh
app_zip="AG_2.35.2_macOS_universal_app-local.zip"
unzip -tq "$app_zip"
hdiutil verify "Psychotic_AG_Fork.dmg"
check_dir=$(mktemp -d)
ditto -x -k "$app_zip" "$check_dir"
app="$check_dir/Antigravity Unlocker.app"
codesign --verify --strict --verbose=2 "$app"
lipo -archs "$app/Contents/MacOS/ag_unlocker"
```

Для универсального пакета `lipo` должен вывести обе архитектуры, `arm64` и `x86_64`. Если нужен выпуск с удостоверением разработчика Apple, это отдельный процесс с подписью Developer ID Application, отправкой через `notarytool` и прикреплением билета. Для такой сборки проверьте извлечённое приложение командами `xcrun stapler validate "$app"` и `spctl --assess --type execute --verbose=4 "$app"`. [Нотарификация приложений в документации Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

## Сборка для Windows

Версия и теги подчиняются тем же правилам, что и для Mac: `v2.35.2` для версии из `Cargo.toml`, `v2.35.2_1` и далее для исправлений анлокера. Тег другого вида останавливает сборку до компиляции.

### Локальная сборка

Нужны Rust, установленный через rustup, и Visual Studio Build Tools с компонентом «Разработка классических приложений на C++». В PowerShell из корня репозитория выполните

```powershell
rustup target add x86_64-pc-windows-msvc
cargo build --release --locked --bin ag_unlocker --target x86_64-pc-windows-msvc
```

Готовый файл появится в `target\x86_64-pc-windows-msvc\release\ag_unlocker.exe`. Для сборки исправления перед `cargo build` задайте полную версию: `$env:AG_FULL_VERSION = '2.35.2_1'`.

Не задавайте `RUSTFLAGS` для этой сборки. Переменная заменяет флаги таргета из [`.cargo/config.toml`](../.cargo/config.toml), и EXE теряет статически слинкованный CRT. На чистой Windows 10 такой файл не запускается с ошибкой «VCRUNTIME140.dll не найден». Если `RUSTFLAGS` всё же нужна, добавьте в неё `-C target-feature=+crt-static`.

### GitHub Actions

- При пуше в `main`, в pull request, при пуше тега `v*` и при ручном запуске workflow собирает EXE для x86-64 и называет его по полной версии: `AG_<версия>.exe`.
- Затем CI проверяет готовый файл. EXE должен весить больше 2 МБ и не требовать VCRUNTIME140.dll. Запуск с `--version` должен вернуть код 0 с версией и канарейкой релиза. Запуск с `--status` должен вернуть код 0, 1 или 2 с полной версией в первой строке. На раннере Antigravity не установлен, поэтому ожидается код 2.
- EXE и отчёты проверки сохраняются как артефакт запуска `AG_<версия>_windows`. После загрузки артефакта выполняются тесты с `-D warnings`. Если тесты не прошли, запуск помечается ошибкой, а артефакт остаётся доступным.
- Релиз на GitHub этот workflow не создаёт и в существующие релизы файлы не добавляет. Релизы публикует только workflow macOS.
