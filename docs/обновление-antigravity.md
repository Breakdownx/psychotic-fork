# Что делать, когда выходит новая версия Antigravity

Гайд про **бамп версии приложения, которое мы патчим** (сам Antigravity: Desktop,
IDE, CLI), а не про выпуск новой версии анлокера. Выпуск анлокера — в самом
конце, в приложении.

---

## Короткий ответ

В 90% случаев делать не нужно **ничего**. Анлокер патчит заново сам после
каждого авто-апдейта Antigravity — этим занимается watchdog
([src/watchdog.rs](../src/watchdog.rs)), который видит новый `language_server`,
ждёт, пока файл «устаканится», и накладывает патч (`Repatched`). Это и есть смысл
решения D27/I19.

**Действовать нужно только в одном случае:** когда анлокер говорит, что **сигнатура
пропала**. Тогда новая сборка Antigravity поменяла то, за что цепляется патч, и
надо найти новое место и обновить сигнатуру в коде.

Сообщения-триггеры, по которым это видно:

- в карточке / логе: **«эта сборка Antigravity анлокеру ещё не знакома, файлы не
  тронуты. Нужна новая версия анлокера»** ([src/ops.rs:1656](../src/ops.rs));
- **«Сигнатура в Language Server не найдена — вероятно, вышла новая версия
  Antigravity»** ([src/main.rs:538](../src/main.rs));
- **«Сигнатура не найдена (возможно, установлена другая версия)»** — для IDE
  `main.js` / `extension.js` ([src/patch_ide.rs](../src/patch_ide.rs)).

Если же карточка после апдейта просто стала зелёной («Работает») — всё, разошлись.

## Что именно трогает патч (что может «уехать»)

Когда Antigravity обновляется, сломаться может ровно одно из пяти. Держи это
перед глазами — отсюда и диагностика.

### 1. Переименования в нативных бинарниках (главное)

Патч — это две **побайтовые замены одинаковой длины** в `language_server` и `agy`:

| из | в | где задано |
|----|----|-----------|
| `ineligible` | `inexigible` | `field_signatures()` — [patch_binary.rs:391](../src/patch_binary.rs) |
| `https_proxy` | `AG_LS_PROXY` | `proxy_var_original()` [:404], `PROXY_VAR_NEW` [:527] |

Критично: **длина должна совпадать** (10 и 11 байт). Весь трюк «переименование без
смещений» держится на равной длине — новый литерал обязан быть такой же длины,
иначе патч так работать не будет.

### 2. Где лежат эти бинарники

`binary_targets()` — [patch_binary.rs:646](../src/patch_binary.rs). Там
перечислены `agy`/`agy.exe`, `resources/bin/language_server(.exe)`, встроенный в
IDE `extensions/antigravity/bin/language_server*` (с глобом по платформенному
суффиксу) и `~/.gemini/bin`. На macOS путь к `Resources` даёт
`macos::resources_dir()`. Если Antigravity **переименует или переместит** бинарник
— правка здесь.

### 3. Архитектура Desktop (JS или нет)

`is_new_desktop_architecture()` — [patch_ide.rs:243](../src/patch_ide.rs).
С версии 2.4+ вся авторизация ушла в `language_server`, а `dist/main.js`
Desktop больше не патчится. Определяется по маркерам `./languageServer` +
`./ipcHandlers` и отсутствию старых `_handleAuthErrorResponse` / `getUserStatus` /
`"AUTH_SUCCESS"` / `"SET_INELIGIBLE"`. Если Google снова поменяет компоновку shell —
проверять и, возможно, чинить эту функцию и `process_install`
([src/main.rs:424](../src/main.rs)).

### 4. Регекс патча IDE `out/main.js`

`patch_ide()` — [patch_ide.rs:159](../src/patch_ide.rs). Это длинный regex по
функции обработки авторизации. Самое хрупкое к обновлениям IDE: при смене их кода
regex перестаёт матчиться → `SignatureMissing`.

### 5. Регекс патча `extension.js`

`patch_extension_js()` — [patch_ide.rs:635](../src/patch_ide.rs). Косметика рядом
с основным патчем, но тоже завязана на их код.

## Пошагово после выхода новой версии Antigravity

1. **Дай Antigravity обновиться** и открой анлокер (или дождись автопатча, если
   включён обход/watchdog). Нажми «Включить всё».
2. **Зелёная карточка «Работает»** → конец. Ничего делать не надо.
3. **«…не знакома» / «Сигнатура не найдена»** → перейди к диагностике ниже.
4. **macOS, «macOS не даёт пропатчить Antigravity»** → это не смена сигнатуры, а
   права: см. раздел про macOS.

### Диагностика сигнатуры (скопируй и запусти)

Проверить, на месте ли литералы в новом бинарнике:

```bash
BIN=/Applications/Antigravity.app/Contents/Resources/bin/language_server
echo "ineligible: $(LC_ALL=C grep -c -a -o ineligible "$BIN")  inexigible: $(LC_ALL=C grep -c -a -o inexigible "$BIN")"
echo "https_proxy: $(LC_ALL=C grep -c -a -o https_proxy "$BIN")  AG_LS_PROXY: $(LC_ALL=C grep -c -a -o AG_LS_PROXY "$BIN")"
```

Как читать результат:

- `inexigible`/`AG_LS_PROXY` > 0 → **уже пропатчен**, всё хорошо.
- `ineligible`/`https_proxy` > 0, а патченных нет → литерал **на месте**, значит
  проблема не в сигнатуре, а в пути/обнаружении (смотри `binary_targets`) или в
  правах записи (macOS, см. ниже).
- Ни тех, ни других нет → **литерал изменился**. Google переименовал поле. Надо
  вскрыть бинарник (`strings`, дизассемблер) и найти новое имя проверки
  непригодности / новую переменную прокси, затем обновить `field_signatures()` /
  `proxy_var_original()` — **с сохранением длины**.

Какой процесс сейчас реально запущен (та ли это версия):

```bash
pgrep -fl "Antigravity.app/Contents/Resources/bin/language_server"
```

### Если сломался IDE / extension

Признак — `SignatureMissing` от `repatch_ide_js` / `patch_extension_js`. Открой
обновлённый `out/main.js` (или `extension.js`), найди кусок, который раньше
матчился regex’ом, и подгони regex в [patch_ide.rs](../src/patch_ide.rs) под новый
код. Патч написан fail-safe: если regex не совпал, файл **не трогается** — поэтому
кривой апдейт не ломает Antigravity, он просто показывает свою ошибку, пока ты не
выпустишь новую сигнатуру.

## macOS: отдельная засада

На macOS патч ложится только если анлокер **может писать** в бандл
`/Applications/Antigravity.app`. Свежеобновлённый из апдейтера бандл macOS
защищает правами **App Management (TCC)**, и анлокер, запущенный двойным кликом
из Finder, этих прав не наследует → запись падает с EPERM, а настольный клиент
остаётся непропатченным (даже когда CLI патчится нормально).

Начиная с фикса от 2026-11-25 это **прямо видно**: карточка пишет «macOS не даёт
пропатчить Antigravity» с шагами, а подпись под «Разблокировкой входа» —
«macOS не даёт изменить Antigravity — включите „Управление приложениями"»
(логика: `macos::write_blocked_by_app_management` + `Status.patch_blocked`, см.
[src/ops.rs](../src/ops.rs) и [src/gui/status.rs](../src/gui/status.rs)).

Что сказать пользователю / сделать самому:

- Системные настройки → Конфиденциальность и безопасность → **Управление
  приложениями** → включить **Терминал** (или программу, из которой запускается
  анлокер), затем «Включить всё».
- Либо запускать через `Запустить.command` **из Терминала**, у которого это право
  есть (двойной клик по самому бинарнику репарентит процесс на launchd и теряет
  грант).

Переподпись (ad-hoc, без hardened runtime) и снятие quarantine делаются
автоматически в `write_atomic` / `macos::resign` — тут вручную ничего не надо.

## Приложение: выпуск новой версии анлокера

Это нужно, **только если** смена сигнатуры заставила править код (пункты 1–5
выше) и надо доставить обновление пользователям.

Где бампается версия:

- [Cargo.toml:3](../Cargo.toml) — `version = "X.Y.Z"`.
- [build_rust.py:1112](../build_rust.py) — `VERSION = "X.Y.Z"` (должна совпадать с
  Cargo.toml).

Про ключи (важно, чтобы не сломать людям вход):

- Ключи солятся по **MAJOR.MINOR** (`env!("CARGO_PKG_VERSION")`, обрезанный до двух
  чисел — [src/auth.rs](../src/auth.rs)).
- **PATCH-бамп** (2.35.0 → 2.35.1): старые ключи 2.35 продолжают работать, новые
  ключи постить не нужно.
- **MAJOR/MINOR-бамп** (2.35.x → 2.36.0): ключи 2.35 перестанут подходить —
  сгенерировать и выложить в группу **новые** ключи на 2.36.

Сборка — через `build_rust.py` (он сам кладёт DerivedData-аналог в
устойчивый target-dir, переподписывает и собирает под macOS-таргет). После
зелёных тестов и релиза — почистить свой временный `target-dir`/`*.xcresult`,
если создавал.

## Чек-лист одним взглядом

- [ ] Antigravity обновился → открыл анлокер, нажал «Включить всё».
- [ ] Карточка зелёная? → готово, дальше не читать.
- [ ] «…не знакома»/«Сигнатура не найдена»? → `grep` литералов в бинарнике.
- [ ] Литерал на месте, но не патчит? → `binary_targets` (путь) или права macOS.
- [ ] Литерала нет? → найти новый, обновить `field_signatures`/`proxy_var_original`
      (та же длина!), при нужде regex в `patch_ide.rs`.
- [ ] macOS не пишет? → App Management Терминалу / запуск из Терминала.
- [ ] Поправил код? → бампнул `Cargo.toml` + `build_rust.py`, при MINOR-бампе —
      новые ключи, собрал, протестировал, выпустил.
